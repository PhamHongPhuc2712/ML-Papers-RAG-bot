# One RAG experience (M6, reassigned 2026-10-15): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Decision (the developer, 2026-10-15).** The product becomes **RAG only, like Consensus**.
There is no separate search mode: every request, including "find me papers about X", goes
through one turn that searches, reads the top papers and answers with citations. The ranked
papers that turn read are shown with the answer as its **References**, not on a page of their
own. Consensus works this way. Its answer header shows the searches it ran and the papers it
read, a cited report follows, and the paper list sits behind "References" and "Filter".

**Goal:**
- One entry point.
- One retrieval configuration.
- An answer that works for both questions and paper-finding requests.
- A References panel listing the papers the answer was built from.

**Why.** The search page and the chat ran the same `SearchService`, but with different reranker
settings: the search page's reranker read title + abstract, the chat's title + the passage that
found the paper (`configs/chat.yaml` overrides). On three "find papers" requests (2026-10-15,
live stack) only 4/9, 3/10 and 6/8 of the chat's papers were in the search page's top 10, so the
same request gave two different answers. One turn with one configuration removes that.

**What this plan supersedes.**
- **The search page as a product surface:** `/`'s `SearchView`, and `POST /v1/search` as a
  public feature.
- **S3's registered decision** (`configs/experiments/m5-rerank-text-v2*.yaml`, commit `ae6a019`).
  It asked which text the *search page's* reranker should read, and with no search page the
  question no longer exists. It is withdrawn **before any S3 number was read**. The topic query
  set it built stays, as an evaluation set for the single first stage (U4).

**Status:** Reviewed 2026-10-15; the four open choices are decided (below). No task started; implementation waits for the developer's go-ahead. The code still
serves the search page and the chat separately until U3 lands.

## Settings (the developer's answers, 2026-10-15)

- **One retrieval configuration:** the chat's measured first stage becomes `configs/search.yaml`
  itself: `rerank.text: title_chunk` and a 2.5 s rerank deadline, the setting behind ORB's frozen
  answering result (0.880). `configs/chat.yaml` loses its `search.overrides`.
- **One search per turn, 10 papers read:** unchanged from the 2026-10-11 answers, confirmed
  2026-10-15. Several model-rewritten searches and 20 papers (Consensus Pro) were declined for
  now, being slower and dearer per turn; either can be added later as its own registered change.
- **Sign-in:** required to ask, because every turn spends; the daily cap stays $3. Paper pages
  (`/papers/[id]`) stay public, as citation targets. `POST /v1/search` stays in the API for the
  turn, the evaluation harness and the paper pages' related papers, but leaves the web app.
- **References:** the turn's own ranked list (20, the first 10 read), with title, venue and year,
  links to paper pages, and client-side year and venue filters.

## Choices decided (the developer, 2026-10-15)

1. **Anonymous use:** none. Sign-in is required to ask, because every turn spends.
2. **Papers read per turn:** 10.
3. **Searches per turn:** one, the follow-up condensed first.
4. **The answer's form:** a structured overview for paper-finding requests (approaches grouped,
   every sentence cited), subject to U2's registered rule. If the overview fails that rule,
   short cited claims stay.
