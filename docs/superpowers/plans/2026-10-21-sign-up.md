# Sign-up and sign-in by emailed code: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** Written 2026-10-21 from the developer's answers below; **to be reviewed before any
task is built.**

**Goal.** Anyone can make an account and sign in with a 6-digit code sent to their email (canvas
boards 2–3). Each account gets 20 answers a day and sees what is left. Settings shows usage and
can delete all chats, and every answer can be marked Helpful or Not helpful. This is the
"sign-up plan" that `2026-10-16-ui-redesign.md` deferred.

## Decisions (the developer, 2026-10-21)

1. **Email goes to a local mailbox for now.** The backend sends through a pluggable SMTP sender. On
   this machine it points at **Mailpit**, a mail catcher in a Docker container: codes appear in its
   web inbox and nothing leaves the laptop. This keeps the spec's zero-budget, on-this-machine rule
   (§2) unchanged. Real delivery (any SMTP server) is a configuration change, made in the
   deployment plan with its own recorded decision.
2. **Codes only; no passwords.** Sign-in and sign-up are one flow: email, then code. An existing
   account signs in with a code sent to its email. `users.password_hash` becomes nullable and
   unused in this plan; dropping it is a later migration once nothing reads it.
3. **20 answers a day per account**, resetting at 00:00 UTC like the spend cap. The $3 daily
   spend cap stays as the global backstop.
4. **Extras in this plan:** usage in Settings, delete all chats, answer feedback.
   "Continue with Google" stays out.

## What changes for people

- **Signed out:** board 1 shows Sign up as well as Log in. Both open one page: enter your email,
  get a code, enter it. An email without an account gets a new account on the first correct code,
  so the page never says whether an email is registered.
- **Signed in:** the ask box shows "N answers left today" once 5 or fewer are left. At 0, sending
  shows board 11's "Daily limit reached" with the reset time.
- **Settings:** account email, answers used today and this month, theme, delete all chats, and
  delete account. Both deletes are confirmed by a code sent to the email; there is no password to
  ask for.
- **Under each answer:** Helpful / Not helpful, changeable, stored with the answer.

## Security rules (fixed here, tested in A1)

- A code is 6 random digits from `secrets`, stored only as an HMAC-SHA256 of (email, code) under a
  key derived from `SECRET_KEY` (as `tokens.token_key` derives the token key), never in plain text
  and never logged.
- It expires after **10 minutes**, works **once**, and allows **5 wrong tries**, after which it is
  dead. Requesting a new code ends every earlier code for that email.
- Limits on asking for codes, per email: one per **60 seconds**, **5 per hour**. Over a limit the
  API answers `429` with `retry_after`. Per-IP limits stay deferred with P5.2's public rate
  limiting: behind the Next.js proxy the API sees one address.
- `POST /v1/auth/code` answers the same `202` for every well-formed email, whether or not it has
  an account, and whether a mail was sent or rate-limited by the per-hour rule. Only the 60-second
  rule is visible, because the page needs it for its resend timer.
- A disabled account (`users disable`) receives no code and cannot verify one.
- The token stays the application-issued JWT (spec §10); the cookie, its lifetime and the proxy
  are unchanged.

## Interfaces

```text
POST   /v1/auth/code     {email}                → 202 {resend_after: 60}
POST   /v1/auth/token    {email, code}          → 200 {access_token, expires_in}   (replaces password)
GET    /v1/me                                   → {user_id, email, usage: {today, month, limit, resets_at}}
POST   /v1/me/code                              → 202   (a code to the signed-in account's email; A4)
DELETE /v1/me            {code}                 → 204   (code from POST /v1/me/code)
DELETE /v1/chats         {code}                 → 204   (all of the caller's chats)
PUT    /v1/chats/{chat}/messages/{message}/feedback  {rating: helpful|not_helpful|null} → 204
POST   /v1/chats/stream  … at the limit         → 429 {code: "daily_limit", resets_at}
```

`frontend/openapi.json` and `lib/api-types.ts` are re-exported after A1, A3, A4 and A5.

### Task A1: Codes, the mail sender and Mailpit

**Files:** `compose.yaml` (a `mailpit` service, pinned image, in the `core` and `test` profiles,
SMTP on `127.0.0.1:1025`, inbox on `127.0.0.1:8025`, no data under `DATA_DIR` because it keeps
nothing worth keeping); migration `0011_login_codes` (`login_codes`: id, email, code_hmac,
created_at, expires_at, attempts, consumed_at; `users.password_hash` nullable); new
`identity/codes.py` (issue, verify, the limits) and `identity/mail.py` (`MailSender` Protocol, an
SMTP sender, a recording fake for tests); `identity/api.py`; `config.py` (`SMTP_HOST`,
`SMTP_PORT`, `MAIL_FROM`, required when accounts are configured, with no default host); the
`users` CLI (`users create EMAIL` without a password, for walk accounts).

- [ ] A code verifies once and only within 10 minutes; the 6th wrong try kills it; a new code ends
  the old one.
- [ ] The per-email limits answer `429` with `retry_after`; the per-hour limit is silent (`202`).
- [ ] An unknown email gets a new account on its first correct code; a disabled account gets no
  mail and cannot verify.
- [ ] The response is the same `202` for an existing and an unknown email.
- [ ] The code never appears in a log line or a stored row (a test greps the captured records and
  the table).
- [ ] An SMTP failure answers `503 mail_unavailable`, retryable, and leaves no live code.
- [ ] Integration: a code really reaches Mailpit's inbox (`GET /api/v1/messages`) in the test
  profile.
- [ ] Backup is unchanged: `login_codes` holds nothing to restore and is not one of the user
  tables.

### Task A3: Twenty answers a day

**Files:** `chat/limits.py` (count and check), `chat/service.py` / `chat/api.py` (refuse at the
limit before anything is spent), `identity/api.py` (usage in `GET /v1/me`), `configs/chat.yaml`
(`daily_answers: 20`), `components/Composer.tsx` ("N answers left today"), board 11's "Daily limit
reached".

- [ ] An answer counts when its assistant message ends `complete` or `insufficient`; a `failed` or
  `interrupted` turn does not, since nothing useful was delivered.
- [ ] Two turns started together at 19 used cannot both pass: the check and the pending message
  are written under a row lock on the user.
- [ ] A replayed request (same `request_id`) is not counted twice.
- [ ] The limit resets at 00:00 UTC; `resets_at` says when.

### Task A4: Settings: usage, delete all chats, delete account by code

**Files:** `chat/store.py` (`delete_all`), `chat/api.py` (`DELETE /v1/chats`), `identity/api.py`
(`DELETE /v1/me` takes a code), `app/account/page.tsx` (board 10), `components/ChatList.tsx`
(empty after delete all).

- [ ] Delete all chats removes only the caller's chats and messages, and leaves today's usage
  count as it was, so deleting does not reset the limit.
- [ ] Both deletes need a fresh code; a wrong or expired code changes nothing.
- [ ] `users delete` (CLI) keeps working without a code.

### Task A5: Helpful / Not helpful

**Files:** migration `0013_message_feedback` (`0012` went to A4's `answer_usage`) (`chat_messages.feedback` in `helpful`,
